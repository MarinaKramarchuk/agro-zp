# Агро-Зарплата & Облік Шляхових Листів — Backend

Node.js (Express) + SQLite. Працює локально (запускачка для обліковця) або
на хостингу (демо на Render — див. «Деплой»). SQL написаний просто, щоб
перенести БД на PostgreSQL для сервера.

## Запуск для обліковця

Подвійний клік на `..\Відкрити облік.bat` у корені проєкту — піднімає сервер
(бекенд роздає зібраний `frontend\dist` сам, окремий Vite-термінал не потрібен)
і відкриває http://localhost:4000 у браузері. Портативний Node лежить у
`..\runtime\` — нічого встановлювати не треба. Закриття консольного вікна
зупиняє програму.

## Запуск для розробки

```bash
cd backend
npm install
cp .env.example .env        # за потреби змінити порт / шлях до БД
npm run db:migrate          # створити таблиці
npm run seed:demo           # наповнити демо-даними (працівники, техніка, поля, тарифи, шляхові)
npm run dev                 # http://localhost:4000/api
```

Корисні команди:

| Команда | Дія |
|---|---|
| `npm run db:reset` | видалити БД і створити структуру заново |
| `npm run seed:demo` | наповнити чисту БД вигаданими демо-даними |
| `npm run start:prod` | міграція + демо-дані в порожню БД + запуск (для хостингу) |

## Деплой

Render Web Service за `../render.yaml`: `npm ci`, старт — `npm run start:prod`
(`migrate.js` → `seed-demo-data.js --if-empty` → `server.js`), health check —
`/api/health`. `PORT` задає Render. Диск безкоштовного плану ефемерний: БД,
`uploads/` і `backups/` зникають при перезапуску, і база знову наповнюється
демо-даними. Для постійних даних потрібен диск/том (платний план Render,
Railway, Fly.io) з `DB_PATH` на нього, або перехід на PostgreSQL.
Фронтенд розгорнутий окремо на Vercel і проксує `/api/*` сюди
(`frontend/vercel.json`).

## Тести

Вбудований тест-раннер Node.js (`node --test`), без зайвих залежностей. Кожен
тестовий файл піднімає застосунок на випадковому порту з чистою тимчасовою
SQLite-БД (`tests/helpers/testApp.js`) — реальні дані в `data/agro.db` не
чіпаються.

```bash
npm test              # усі тести (tests/unit + tests/integration)
npm run test:coverage # те саме + звіт покриття
```

`tests/unit/` — чиста бізнес-логіка без HTTP (розрахунок суми, підбір тарифу,
колір комірки табеля, валідація, трансляція помилок SQLite).
`tests/integration/` — наскрізні HTTP-тести через `fetch` проти `createApp()`
(шляхові листи, табель, відомість ЗП, CRUD-довідники, тарифи).

## Модель даних

Тарифи — **простий редагований довідник актуальних розцінок** (без наказів та історії):

```
work_types (вид робіт)
   └── tariff_rates (розцінка: техніка × інвентар × одиниця виміру)
            ├── rate — одна ставка, нараховується одній людині
            ├── secondary_* — складені тарифи, напр. "72,5 грн/год + 5 грн/т"
            ├── is_manual — тариф "від мінімалки": суму вводить обліковець
            └── tariff_rate_models → equipment_models (МТЗ, Джон Дір, ДАФ, Claas ...)
routes (міжміські рейси: фіксована сума за рейс, км в дві сторони)
route_km_rates (грн/км за діапазонами відстані)
employees (+ особистий оклад за місяць monthly_rate) · equipment · fields
worklogs (шляхові листи)
```

Одиниці виміру (`unit`): `ha` (га), `ton` (т), `km`, `tkm` (т·км), `hour` (год),
`trip` (ходка/рейс), `bale` (тюк), `day` (день).

Довідники не мають статусів активний/неактивний — лише видалення запису.

### Як рахується сума запису

Кожен запис шляхового листа має `pay_mode`:

- **`'tariff'`** (за замовчуванням) — за видом робіт. Розцінка береться
  з довідника тарифів (`tariff_rate_id`), з міжміського маршруту (`route_id`)
  або **вводиться вручну прямо в шляховому** (`manual_rate` + `unit`), якщо
  підходящого тарифу немає в довіднику — тоді `tariff_rate_id` і `route_id`
  лишаються `NULL`.
- **`'hourly'`** — погодинно за особистим окладом працівника (`employees.monthly_rate`,
  грн/місяць); якщо оклад не вказано — автоматично береться поточна мінімальна
  ЗП (`payroll_settings.minimum_wage`, редагується на сторінці "Працівники").
  Погодинна ставка = (оклад або мінімальна ЗП) / норма робочих годин місяця
  (будні дні місяця запису × `NORMAL_SHIFT_HOURS`); розцінка = ставка,
  обсяг = `hours`. `422`, лише якщо не задано **ні** оклад, **ні** мінімальну ЗП.

```
обсяг         = показник за одиницею виміру (га / т / год / ходки / т·км = км × вантаж)
РАЗОМ         = rate × обсяг  + secondary_rate × обсяг_другої_складової
```

`manual_amount` (для тарифів «від мінімалки») перекриває весь розрахунок.
Розцінка й суми зберігаються в самому записі (snapshot), тому зміна тарифу
не переписує вже нараховану ЗП за минулі дні.

**Доплата "хімік 50%"** (`helper_absent`) — коли хімік був відсутній, водій-
оприскувач бере на себе його роботу і отримує 50% від тарифу хіміка за
оброблену площу (`area_ha`), як якби хімік сам відпрацював цю площу:

```
хімік_розцінка = helper_rate                     (знімок обраного tariff_rates)
доплата        = 0.5 × хімік_розцінка × area_ha  (= helper_amount)
РАЗОМ          = сума за тарифом + доплата
```

Доступно лише при `pay_mode: 'tariff'` і потребує `helper_tariff_rate_id` —
тариф хіміка обирається вручну з довідника (без жорсткої прив'язки "вид
оприскування → тариф хіміка"), і має належати виду роботи з `is_helper_role
= 1` (напр. "Помічник (хімік)") — інакше `422`. `helper_rate` зберігає ПОВНУ
(не половинну) ставку хіміка на момент збереження, для прозорості в
друкованих формах.

**Оплата за транспортним тарифом** (`transport_pay`) — фактичний вид робіт і
обсяг (напр. "Дискування", `area_ha`) фіксуються як завжди (і йдуть у Контроль
гектарів без змін), але сума рахується не за тарифом цього виду робіт, а як:

```
транспортна_ставка = ставка тарифу work_types.is_transport_rate (unit='hour', підбирається за технікою)
РАЗОМ  = transport_rate × hours
```

`unit`/`rate`/`quantity` запису лишаються "інформаційними" — реальним
тарифом обраного виду робіт (для друку/журналу), а `total_amount` вже
повністю замінено транспортним.
Доступно лише при `pay_mode: 'tariff'`, потребує `hours > 0`; у довіднику
"Види робіт" має бути позначений рівно один вид робіт `is_transport_rate = 1`
("Транспортні роботи по господарству") — інакше `422`. Ставка підбирається за
технікою запису (`equipment_id`), як і звичайний тариф; якщо техніка не
вказана або не належить жодній з груп у довіднику — береться ставка,
позначена "типовою" (`tariff_rates.is_default_rate`, напр. МТЗ/Джон Дір) —
якщо жодну не позначено, `422`. Не поєднується з доплатою "хімік 50%" в
одному записі.

Один шляховий лист — завжди одна людина (двох працівників в одному записі
не буває). Запис може охоплювати кілька дат (`work_date`..`work_date_to`,
напр. дальній рейс): у Табелі години й сума показуються на кожен день
періоду, а у Відомості ЗП сума враховується один раз.

### Табель (кольори комірок)

Береться **сума годин за день** по всіх шляхових листах працівника:

| Годин | `status` | Колір |
|---|---|---|
| 0 (немає листа) | `empty` | сірий |
| 1–8 | `normal` | зелений |
| > 8 | `overtime` | яскраво-червоний, повертається `overtime_hours` |
| є лист, години не внесені | `no_hours` | окремий стан (сигнал обліковцю дозаповнити) |

Норма зміни налаштовується: `NORMAL_SHIFT_HOURS` (за замовчуванням 8).

## API

Базовий шлях `/api`. Помилки: `{ "error": "...", "details": [...] }`,
коди `400` (некоректний запит), `404` (не знайдено), `409` (запис використовується),
`422` (валідація / не вибрано тариф).

### Довідники (CRUD: `GET /`, `GET /:id`, `POST /`, `PUT|PATCH /:id`, `DELETE /:id`)

| Ресурс | Фільтри списку |
|---|---|
| `/employees` | `staff_group` (`driver`/`tractor`/`other`), `q` |
| `/equipment` | `category`, `model_id`, `q` |
| `/equipment/models` | `category`, `q` — марки техніки з тарифів |
| `/fields` | `crop`, `q` |
| `/work-types` | `staff_group`, `is_helper_role`, `is_transport_rate`, `q` |
| `/tariffs` | `work_type_id`, `equipment_id`, `unit`, `staff_group`, `q` |
| `/routes` | `q` — міжміські рейси |
| `/routes/km-rates` | ставки грн/км за діапазонами |

Додатково:

- `GET /work-types/units` — одиниці виміру та обов'язкові показники для динамічної форми
- `GET /work-types/with-rates` — види робіт із кількістю тарифів
- `GET /work-types/:id/rates?equipment_id=` — варіанти тарифів для роботи
- `GET /tariffs/resolve?work_type_id=&equipment_id=&unit=` — підбір тарифу;
  якщо варіантів кілька, повертає `422` зі списком у `details.variants`
- `PUT /tariffs/:id/models` — `{ "model_ids": [1,2] }` привʼязка марок техніки
- `GET /routes/estimate?route_id=` або `?distance_km=` — сума рейсу (за довідником або грн/км)

### Шляхові листи

- `GET /worklogs?date_from=&date_to=&date=&employee_id=&equipment_id=&field_id=&work_type_id=&route_id=&confirmed=&limit=&offset=`
- `POST /worklogs/preview` — **розрахунок «на льоту»** до збереження (сума за запис у формі)
- `POST /worklogs`, `PUT|PATCH /worklogs/:id` (перерахунок автоматичний), `DELETE /worklogs/:id`
  — усі три повертають **`409`**, якщо `work_date`..`work_date_to` запису
  (старе й/або нове значення при `PUT|PATCH`) потрапляє в закритий місяць —
  див. «Замикання періоду» нижче

Тіло запису:

```json
{
  "work_date": "2026-07-06",
  "work_date_to": null,
  "employee_id": 1,
  "equipment_id": 6,
  "field_id": 1,
  "work_type_id": 47,
  "tariff_rate_id": 79,
  "route_id": null,
  "pay_mode": "tariff",
  "hours": 9.5,
  "area_ha": 12.5,
  "tons": null, "distance_km": null, "cargo_tons": null,
  "trips": null, "bales": null, "days": null,
  "cargo_type": null,
  "manual_rate": null,
  "manual_amount": null,
  "helper_absent": false, "helper_tariff_rate_id": null,
  "transport_pay": false,
  "note": null,
  "confirmed": false
}
```

`tariff_rate_id` можна не передавати — тариф підбереться за роботою і технікою;
якщо підходить кілька, API повертає список варіантів для вибору у формі.
`hours` варто вносити завжди — на них тримається табель.
`work_date_to` — необов'язково; порожньо = один день (= `work_date`).
`pay_mode: 'hourly'` — погодинно за `employees.hourly_rate` (тоді `tariff_rate_id`,
`route_id`, `manual_rate` не потрібні). `manual_rate` — розцінка вручну, коли
в довіднику немає тарифу для цієї роботи (потрібен `unit`).
`helper_absent: true` + `helper_tariff_rate_id` — доплата "хімік 50%", див. вище.
`transport_pay: true` — оплата за транспортним тарифом (замість тарифу виду
робіт), див. вище.
`cargo_type: 'chaff' | 'grain_waste'` — вид вантажу для транспортних рейсів
(напр. САЗ везе полову чи зерновідходи); суто інформаційне поле, на суму не
впливає — так само, як `cargo_tons`/`distance_km` для рейсів ДАФа вище.
`confirmed: true` — обліковець звірила запис з паперовим шляховим листом
водія; не впливає на розрахунок і не пов'язано з `hecterra_activity_id`/
`area_ha_auto` (це лише підказка з GPS при заповненні) — сервер сам це поле
ніколи не змінює й не скидає при інших правках запису.

- `GET /worklogs/waybill.xlsx?employee_id=&date_from=&date_to=&template=68|2|67b&channel=bank|cash&org_name=&equipment_id=`
  — друкований бланк за період. `template=68` (Дорожній листок трактора) і
  `template=2` (типова форма №2, вантажівка) — **точна копія** офіційного
  Excel-бланка з кореневої папки `шаблони/` (`waybillTemplateService.js`):
  один аркуш книги на кожен робочий день, реальні дані (ПІБ, техніка,
  поле/вид роботи/культура/обсяг/розцінка) вписані в комірки шаблону поверх
  друкованих підписів; технічні поля без відповідника в моделі даних
  (шифри, категорії, тонно-кілометри, підписи/штампи) лишаються порожніми
  для ручного заповнення, як і на паперовому бланку. `template=67b`
  (Обліковий лист тракториста-машиніста) офіційного зразка не має — це
  власний макет програми (`aoa_to_sheet`), як і раніше.

### Табель

- `GET /timesheet?year=2026&month=7[&employee_id=]` — сітка
  «працівники × дні»: у кожній комірці `hours`, `entries`, `overtime_hours`,
  `amount_p`, `amount_l`, `total_amount`, `status`; є підсумки по рядку.
  Шляховий, що охоплює кілька дат, дублює свої `hours`/суму на кожен день
  періоду (для Відомості ЗП сума рахується один раз — див. нижче)
- `GET /timesheet/day?employee_id=1&date=2026-07-06` — деталізація дня для pop-up
  (техніка, поле, виробіток, суми, понаднормові)

### Відомість ЗП

- `GET /payroll/summary?date_from=&date_to=&employee_id=&staff_group=` — зведена
  таблиця: днів, годин (у т.ч. понаднормових), га, тонн, км, т·км, ходок, тюків, П, Л, разом
- `GET /payroll/summary.xlsx?...` — та сама відомість у Excel
- `GET /payroll/employee/:id?date_from=&date_to=` — деталізація по днях
- `GET /payroll/employee/:id/export.xlsx?...` — Excel для «корінця»

#### Замикання періоду

Після того, як відомість за місяць сформована й виплачена, місяць можна
закрити — тоді `worklogs` (create/update/delete), чиї `work_date`..`work_date_to`
потрапляють у цей місяць, повертають `409`, доки місяць не відкрито назад
(`periodLockService.js`, таблиця `locked_periods`). Ніякого підтвердження чи
ролей на бекенді немає — рішення закрити/відкрити повністю на обліковці.

- `GET /payroll/locked-periods` → `{ items: [{ year, month, locked_by, locked_at }] }`
- `POST /payroll/locked-periods` `{ year, month, locked_by? }` — закрити місяць
  (повторний виклик того самого місяця лише оновлює `locked_by`/`locked_at`)
- `DELETE /payroll/locked-periods/:year/:month` — відкрити назад (ідемпотентно, `204`)

### Службові

- `GET /health`, `GET /stats`
- `POST /integrations/gektera/fields` — зарезервовано під імпорт полів із Gektera (`501`)

## Демо-дані

`scripts/seed-demo-data.js` наповнює чисту БД вигаданими даними (працівники,
техніка, поля, тарифи, маршрути, шляхові листи) — зручно для першого запуску
чи демонстрації. Запускати лише на порожній/тестовій БД: перевіряє наявність
реальних даних і без явного прапорця відмовляється чистити непорожню базу.

## Наступні кроки

- PDF-експорт: зараз є Excel; PDF найпростіше робити з фронтенду через друк
  сторінки відомості (або додати серверний рендер за потреби).
- Перенесення на PostgreSQL: замінити `INTEGER PRIMARY KEY AUTOINCREMENT`,
  `datetime('now')` та вираз-індекс `IFNULL(...)` на аналоги PostgreSQL.
